# Ethiopia Malaria Burden Forecasting & Supply Chain Dashboard

Forecasts woreda-month malaria case counts with **XGBoost** and a **GRU**
neural network, optimizes a limited antimalarial (AL course) supply budget
across woredas with a **linear program**, and serves all of it through a
**password-protected Streamlit dashboard**.

## Repo layout

```
malaria-dashboard/
├── app.py                       # Streamlit dashboard (login + 3 tabs)
├── requirements.txt             # deps needed to RUN the dashboard
├── requirements-train.txt       # extra deps needed to RE-TRAIN models
├── .streamlit/
│   └── secrets.toml.example     # template for login credentials -- copy, edit, never commit
├── .gitignore
├── data/
│   ├── model_frame.csv                        # main modeling panel (984 woredas x 72 months)
│   ├── model_frame_dictionary.csv             # column definitions
│   └── woreda_monthly_rainfall_2019_2024.csv  # raw rainfall (reference; already summarized into model_frame)
├── src/
│   ├── train_xgboost.py         # trains the XGBoost forecaster
│   ├── train_gru.py             # trains the GRU forecaster
│   ├── generate_forecast.py     # 6-month forward forecast (used by the dashboard's map/drill-down)
│   └── optimize_supply_chain.py # LP allocation of AL courses across woredas
├── models/                      # trained model artifacts (committed, already run once for you)
├── outputs/                     # forecasts, allocation tables, and interactive HTML plots
└── notebooks/
    └── malaria_forecasting_dashboard.ipynb   # the original end-to-end Colab notebook
```

> **Note on data:** `Woreda_Yearly_NDVI_2019_2024.csv` (the raw NDVI + woreda
> polygon file, ~34 MB) is not included here because none of the code reads
> it directly — its NDVI/EVI/LAI values are already merged into
> `model_frame.csv`. Add it to `data/` yourself (with Git LFS if you're near
> GitHub's 100 MB file limit) if you want the raw source alongside the
> derived table for audit purposes.

These were generated by actually running the scripts in `src/` against
`data/model_frame.csv` — nothing here is a placeholder.

| Model | RMSE | MAE |
|---|---:|---:|
| Baseline (train-mean) | 2,213 | — |
| XGBoost (Tweedie objective) | 2,035 | 794 |
| GRU (6-month window) | 1,631 | 484 |

See `outputs/xgb_metrics.json` and `outputs/gru_metrics.json` for the exact
numbers, and `outputs/*_feature_importance.html` / `outputs/gru_training_curve.html`
for the interactive plots (open directly in a browser, no server needed).

**2024 AL-course allocation** under a 70%-of-need budget with an equity floor:

| Burden tier | Woredas | Need | Allocated | Coverage |
|---|---:|---:|---:|---:|
| Very high | 50 | 2,876,319 | 1,661,605 | 58% |
| High | 147 | 4,053,855 | 2,500,034 | 62% |
| Moderate | 295 | 2,600,422 | 2,366,137 | 91% |
| Low | 492 | 478,804 | 478,804 | 100% |

**⚠️ Known issue in the current allocation policy:** the LP objective
maximizes "coverage per course spent," which mathematically favors cheap,
low-need woredas over expensive, high-burden ones — visible above as "low"
tier hitting 100% while "very high" sits at 58%. The equity floors (50%/30%
guaranteed minimums) partially compensate but don't fully fix this. If you
need a policy that strictly exhausts high-burden tiers before touching
lower tiers, the objective in `src/optimize_supply_chain.py` needs a
tier-lexicographic rewrite — ask if you want that version.

## Running the dashboard locally

```bash
git clone <your-repo-url>
cd malaria-dashboard
pip install -r requirements.txt

cp .streamlit/secrets.toml.example .streamlit/secrets.toml
# edit .streamlit/secrets.toml: set real usernames/passwords and a random cookie key
# generate a random key with:  python -c "import secrets; print(secrets.token_hex(32))"

streamlit run app.py
```

Open the printed `http://localhost:8501` link and log in with the
credentials you set.

## Deploying so other people can access it via a link

**Recommended: Streamlit Community Cloud (free, persistent URL, HTTPS).**

1. Push this repo to GitHub (public or private).
2. Go to [share.streamlit.io](https://share.streamlit.io), sign in, click
   "New app", and point it at this repo + `app.py`.
3. In the app's **Settings → Secrets** panel, paste the contents of
   `.streamlit/secrets.toml.example` with real values filled in (this is
   where your actual usernames/passwords/cookie key live — never commit
   them to the repo itself).
4. Deploy. You get a stable link like `https://yourapp.streamlit.app` that
   anyone with the username/password can log into, and that keeps working
   even when your laptop or Colab session is closed.

**Alternative: Colab + localtunnel.** Works for a same-day demo but the
link breaks every time the Colab runtime restarts and traffic goes through
a public tunnel relay — not meant for real users or sensitive data. See the
last two cells of `notebooks/malaria_forecasting_dashboard.ipynb` if you
want this quick-and-dirty option instead.

## Re-running / retraining

```bash
pip install -r requirements-train.txt

python src/train_xgboost.py          # -> models/xgb_malaria_model.json
python src/train_gru.py              # -> models/gru_malaria_model.keras
python src/generate_forecast.py      # -> outputs/forecast_df.csv (needs the XGBoost model)
python src/optimize_supply_chain.py  # -> outputs/*_need_vs_allocation_2024.csv
```

Tune the policy knobs at the top of `optimize_supply_chain.py`
(`BUDGET_FRACTION_OF_NEED`, `FLOOR_BY_TIER`, `TIER_WEIGHT`,
`TIME_TIEBREAK_WEIGHT`) to explore different funding scenarios.

## Known modeling caveats

- **`burden_tier` leakage:** it's derived from each woreda's full-series
  mean case count, so XGBoost gets a preview of the answer. Real forecasting
  performance (no `burden_tier`) will be worse than the numbers above —
  drop it from `FEATURES` in `src/train_xgboost.py` to check.
- **Tigray conflict window (Nov 2020–Dec 2022):** `cases` is `NaN` there,
  not zero. Both training scripts correctly exclude these rows rather than
  treating them as "no malaria."
- **Forward forecast persistence assumption:** `generate_forecast.py` rolls
  climate lags forward by repeating the last observed value — it does not
  use a real weather forecast. Fine for a rough 1–2 month look-ahead, less
  reliable further out.
